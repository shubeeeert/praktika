# Отчёт по анализу данных сервиса и генерации продуктовых гипотез

## 1. Контекст и цель

**Сервис:** интернет-сервис с клиент-серверной архитектурой, монетизация через подписки по тарифам.  
**Клиенты:** мобильные приложения (Android, iOS, Huawei) и другие клиенты (desktop/web/tv/web-extension по данным устройств).  
**Исходные данные:** дамп серверной БД (CSV-таблицы), структура таблиц (`db_structure/`), логи подключений/инцидентов (в т.ч. `logs.zip`, 4.7 GB), выгрузка предоставлена владельцем сервиса.  
**Источник:** https://disk.yandex.ru/d/UYuFNCrHvWR3DQ

**Цель:** проанализировать и сопоставить данные по клиентам и их действиям, сгенерировать продуктовые гипотезы и подтвердить/опровергнуть их на основе данных.

- Результаты: `analysis/output/profile.json`, `analysis/output/analysis_results.json`, `analysis/output/devices_extra.json`, `analysis/output/analyze.log`.
- Для гипотез использовались только наблюдаемые поля; где данных недостаточно (например, нет байтов трафика), это явно указано.

### 2.3. Качество данных / ограничения

- В `users` много гостей: `guest` = 1,176,913 (63.79%). Это влияет на конверсию и интерпретацию “пользователь”.
- `advertising_ids.csv` в загруженной структуре содержит только `id, created_at` (без явного `user_id`/advertising_id поля в выгрузке) — прямую проверку “один advertising ID на много аккаунтов” по этой таблице сделать нельзя.
- Логи подключений (`proxy_user_connection_logs`) содержат только факт подключения (`user_id,node_id,subscribe_id,created_at`), без объёма трафика в байтах. Поэтому лимиты 500 MB/день и 15 GB/мес нельзя подтвердить напрямую по байтам; можно оценивать косвенно через частоту подключений.
- `task_history` отражает инфраструктурные задачи/ошибки нод (SSH/Remnawave), а не клиентские crash-логи мобильных приложений. Для гипотез по клиентским инцидентам нужен разбор `logs.zip`.

## 4. Гипотеза 1 — Повторная регистрация для использования триала

### 4.1. Формулировка

Среди пользователей есть те, кто заводит новый аккаунт, чтобы пользоваться триал-периодом повторно. Нужно определить признаки и косвенные сигналы в данных.

### 4.2. Данные и проверка

| Проверка | Результат | Интерпретация |
|---|---:|---|
| Пользователи с `trial_used_at` | 22,197 | Триал использовался заметной, но небольшой долей базы |
| Guest с `trial_used_at` | 0 | Триал фиксируется на не-гостевых/клиентских аккаунтах |
| `advertising_ids`: колонки | `id, created_at` | Нет явной связки с `user_id` или advertising ID устройства — прямой дедуп по рекламе невозможен |
| `external_accounts`: одинаковый `account_id` у разных `user_id` | 0 | По внешним аккаунтам явного шаринга не видно |
| `device_code`: одно устройство привязано к нескольким `accepted_by_user_id` | 0 | По device_code явного мультиаккаунтинга не видно |
| `devices`: пользователей с >1 устройством | 203,308 из 1,841,758 | Многоустройственность нормальна; сама по себе не признак абьюза |
| Устройств на пользователя (p50/p90/p95/max) | 1 / 2 / 2 / 143 | max=143 — аномалия, требует ручной проверки |

### 4.3. Косвенные признаки, которые стоит добавить в выгрузку/логи

Для уверенного выявления абьюза триала не хватает связок “устройство/реклама/платёж → аккаунт”. Рекомендуемые признаки:

1. **Advertising ID / IDFA / GAID / AppMetrica device id** в связке с `user_id` и временем активации триала.
2. **Device fingerprint**: `device_identifier`, модель, ОС, версия приложения, IP/ASN, push token hash — искать один fingerprint на N аккаунтов с триалом.
3. **Платёжные реквизиты**: один `saved_payment_method`/card fingerprint/payer id на несколько аккаунтов.
4. **Поведенческий паттерн**: регистрация → активация триала → короткая активность → отсутствие оплаты → новая регистрация с того же устройства/IP.
5. **Email/телефон паттерны**: алиасы, одноразовые домены, похожие локальные части; у реальных client домены в основном массовые (gmail/yandex/mail.ru).

### 4.4. Вывод по гипотезе

**Статус: не подтверждена имеющимися данными, но остаётся высокорискованной.**  
Прямых доказательств повторного триала в текущей выгрузке нет, но это связано с отсутствием ключевых полей связки (advertising/device/payment fingerprint → user). Нужна доразметка данных.

**Рекомендация:** внедрить антиабьюз-правило “один триал на устройство/платёжный fingerprint/рекламный ID” с мягким фоллбэком (manual review), а не только на аккаунт.

## 5. Гипотеза 2 — Оптимальные лимиты трафика для бесплатного тарифа

### 5.1. Формулировка

Бесплатный тариф имеет лимиты 500 MB/день и 15 GB/мес, расширение — за просмотр рекламы. Нужно оценить, оптимальны ли лимиты по реальному потреблению.

### 5.2. Что есть в данных

- Продукты: Basic (id=1, $0, limit_id=1) — бесплатный.
- Подписки: Basic почти отсутствует в `subscribe` как платная подписка (подписки в основном Lite/Silver/Gold/Diamond). Это логично для free.
- `proxy_user_connection_logs.csv`: 340,966 записей; только `id,user_id,node_id,subscribe_id,created_at`. **Нет байтов трафика.**
- В `proxy_user_connection_logs` только 28,665 записей имеют `subscribe_id`, сопоставимый с `subscribe.product_id`; все сопоставленные — платные продукты (2/3/4/5). Прямых логов Basic/free в этой выборке недостаточно.
- `adv_view_history.csv`: 7,552,651 просмотров рекламы, 414,504 уникальных пользователя (22.47% от всех users) — подтверждает, что механизм “реклама за расширение/продолжение” реально используется.

### 5.3. Косвенная оценка по подключениям (proxy logs)

| Продукт | Среднее conn/day | Median | P90 | P95 | Max | Среднее conn/month | Median | P90 | P95 |
|---|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| Lite (5) | 2.94 | 2 | 6 | 9 | 55 | 22.87 | 11 | 61 | 89.1 |
| Silver (2) | 2.40 | 2 | 5 | 6 | 49 | 18.09 | 8 | 45.7 | 63.0 |
| Gold (3) | 2.62 | 2 | 6 | 7 | 16 | 22.28 | 9 | 61 | 70.2 |
| Diamond (4) | 2.38 | 2 | 5 | 7 | 28 | 21.57 | 13 | 53 | 64.2 |

**Важно:** это подключения, не трафик. Один коннект может быть и 10 MB, и 2 GB. Без `bytes_in/bytes_out/duration` нельзя валидировать 500 MB/15 GB.

### 5.4. Использование рекламы как индикатор давления лимитов

| Метрика | Значение |
|---|---:|
| Просмотров рекламы всего | 7,552,651 |
| Пользователей, смотревших рекламу | 414,504 (22.47% всех users) |
| Просмотров на пользователя в день (mean/median/p90/p95/max) | 3.97 / 2 / 9 / 13 / 1886 |
| Просмотров на пользователя в месяц (mean/median/p90/p95/max) | 13.07 / 3 / 30 / 56 / 2181 |

**Интерпретация:** реклама — массовый механизм. Медианный пользователь смотрит мало рекламы (2/день, 3/мес), но хвост большой: P90=30/мес, P95=56/мес, max=2181. Это указывает на сегмент power-users, которые регулярно упираются в ограничения и “расплачиваются” вниманием. Их важно проверить на предмет конверсии в платный тариф: если они смотрят много рекламы, но не покупают, текущий лимит/цена пакета могут быть не сбалансированы.

### 5.5. Что нужно для корректного ответа

1. Выгрузить трафик: `user_id, date, bytes_up, bytes_down, session_duration, product/tariff`.
2. Сегментировать только free/Basic пользователей, исключая trial/paid периоды.
3. Посчитать распределение дневного и месячного трафика: p50/p75/p90/p95/p99.
4. Оценить долю пользователей, упирающихся в лимит, и их последующее поведение: просмотр рекламы, покупка, churn.
5. Посчитать экономику рекламы: сколько ad-view нужно для X MB и как это влияет на конверсию в платёж.

### 5.6. Предварительная продуктовая рекомендация

**Статус: частично подтверждена по сигналу спроса (реклама активно используется), но не подтверждена по байтам.**

Рабочая гипотеза для A/B-теста:
- Оставить дневной лимит как “мягкий” порог, но сделать месячный более гибким (например, 10/15/20 GB) по когортам.
- Измерять не только “достиг лимита”, но и “достиг лимита и не вернулся / посмотрел рекламу / купил”.
- Для heavy-ad сегмента (P90+ просмотров рекламы) тестировать специальный оффер Lite/промо, т.к. они уже демонстрируют высокую вовлечённость.
- Если p90 дневного трафика free-пользователей < 500 MB, лимит не является главным барьером; если p50 упирается в лимит — лимит слишком жёсткий и режет ценность.

## 6. Гипотеза 3 — Как долго пользуются бесплатным тарифом до покупки и роль триала

### 6.1. Формулировка

Как долго люди пользуются бесплатным тарифом до покупки? Всегда ли покупка после триала? Сколько клиентов покупает без триала?

### 6.2. Факты из данных

| Метрика | Значение |
|---|---:|
| Paid orders | 69,942 |
| Paid trial orders | 22,198 (31.74% paid orders) |
| Paid non-trial orders | 47,744 (68.26% paid orders) |
| Уникальных пользователей с оплатой | 29,022 |
| Доля платящих от всех users | 1.57% |
| Доля платящих от client | ~4.34% (29,022 / 667,962) |
| Первый платёж = trial | 22,036 пользователей |
| Первый платёж = non-trial | 6,986 пользователей |
| Платили, но никогда не использовали trial | 6,829 (23.53% платящих) |

### 6.3. Время до первой оплаты

| Сегмент | Mean | Median | P25 | P75 | P90 |
|---|---:|---:|---:|---:|---:|
| Все платящие | 47.29 дн | 15.04 дн | 2.90 дн | 62.22 дн | 137.75 дн |
| Первый платёж = trial | 44.96 дн | 16.30 дн | — | 61.40 дн | — |
| Первый платёж = non-trial | 54.48 дн | 11.51 дн | — | 64.81 дн | — |

### 6.4. Связь trial_used_at и оплаты

| Метрика | Значение |
|---|---:|
| Median days trial_to_paid | -0.00055 дн (~ -48 сек) |
| Mean days trial_to_paid | -0.45 дн |
| P75 / P90 | -0.00034 / -0.00025 дн |
| Покупок в тот же момент/до trial_used_at | 22,192 |

**Интерпретация:** поле `trial_used_at` почти совпадает с моментом первой trial-оплаты (разница секунды, отрицательный знак вероятно из-за порядка записи/округления/часовых зон). Это означает, что `trial_used_at` фиксирует использование trial-покупки, а не “начало бесплатного пробного периода без оплаты”. Триал в данных — скорее платный/символический триал через order/transaction.

### 6.5. Вывод по гипотезе

**Статус: частично подтверждена.**

- Покупка **не всегда** после триала: 23.53% платящих никогда не имели `trial_used_at`.
- Значимая часть платящих начинает с trial-order (22,036 из 29,022 первых оплат).
- Медианное время до первой оплаты — ~15 дней от регистрации; распределение длинное (P90 ~138 дней), значит есть сегмент “долго разогревающихся” пользователей.
- Non-trial первые покупки имеют меньшую медиану (11.5 дн), но более тяжёлый хвост — вероятно, это более осознанные/срочные покупатели.

**Рекомендации:**
- Разделить воронку на `trial-first` и `direct-paid`.
- Для `trial-first` оптимизировать первые 24 часа и 3 дня после триала (onboarding, активация, напоминание до списания/окончания).
- Для пользователей без оплаты после 14–30 дней запускать reactivation-офферы/ограниченные промо.

## 9. Дополнительные гипотезы

### 9.1. Платёжный провайдер влияет на успех оплаты

**Наблюдение:** provider 2 даёт основной объём, но 40% failed; provider 3 имеет много pending.  
**Гипотеза:** маршрутизация по провайдерам/странам/методам оплаты снижает failed rate.  
**Как проверить:** сравнить success rate по provider × country × payment method × device × amount × new/returning.

### 9.2. Высокая доля guest-пользователей искажает продуктовые метрики

**Наблюдение:** 63.79% guest, 1.91% verified.  
**Гипотеза:** часть guest — технические/одноразовые сессии; метрики retention/conversion надо считать по активированным client.  
**Как проверить:** определить “активированный пользователь” (верификация/подключение/сессия>N сек/подписка) и пересчитать воронку.

### 9.3. Реферальная программа недоиспользуется

**Наблюдение:** referral_history 389 строк, referral_code_used 581, referal_balance в users в основном 0.  
**Гипотеза:** реферальная механика либо слабо видна, либо не даёт ценности.  
**Как проверить:** cohort пользователей с реферальным кодом vs без: конверсия, LTV, churn.

## 11. Приоритетный план действий

1. **Доработать телеметрию и выгрузки**: bytes_in/out, adid/idfa/gaid, app version, platform, error_code, payment_method, country.
